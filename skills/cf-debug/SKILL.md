# 代码诊断（Debug the learner's own code）

对象是**学员的代码**，不是"再写一份更好的"。目标是让他自己看懂错在哪。

## 第一步：先定性，再动手

| 学员的问题 | 先做什么 |
|---|---|
| "为什么 WA"（贴了代码） | 拿到题面 → 抽契约 → **用学员的代码**去跑官方样例与随机对拍（`cf_stress` 的 `solCode` 传学员代码，暴力解当标尺） |
| "为什么 TLE" | 不一定要跑：先算复杂度 × 数据范围给出**可判定的结论**（"n=2·10^5 时 O(n²) 是 4·10^10 次，必然超时"）。有反例或实测耗时更好 |
| "我这个做法行不行" | 先 `cf_adjudicate` / 可行性判断（等价性、复杂度和正确性），**判定可行再实测**；不可行就直接说清哪一步断了 |
| "这行什么意思" | 纯解释，不要跑任何东西 |

**不要跳过定性去改代码**：学员贴 WA 代码时，最常见的错误是教练直接甩一份自己的正解——那就变成了"换个题解"，学员还是不知道自己错在哪。

## 第二步：拿到硬证据

- **反例**：`cf_stress`（学员代码 vs 暴力解）→ `cf_minimize` 缩到最小。
  反例的呈现方式必须是"你的输出是 X，正确是 Y，在输入的第 k 个位置分歧，因为……"。
- **实测耗时**：`cf_run` 在大规模数据上的真实毫秒数，用来对照理论复杂度。
- **编译/警告**：C++ 的 UB、未初始化、越界，先修这些再谈逻辑。

拿不到反例时（比如只有样例、或暴力解建不出来）**要明说**："我只用复杂度给出了判断，没有实测反例。"

## 第三步：怎么讲

固定顺序，但不许铺垫：

1. **第一句就是根因**。不要先夸代码、不要先复述题意。
   ❌ "你的代码整体思路是对的，不过有一个小问题……"
   ✅ "错在 `ans` 用了 `int`：`n=2·10^5` 且 `a_i=10^9` 时和是 `2·10^14`，第 3 行就溢出了。"
2. **为什么**：从哪一步开始错的、机制是什么、改哪个量能救回来。
3. **最小反例手算**：把这个反例一步步走一遍，让他能自己复现。
4. **改法**：完整可提交的实现，或精确到"把第 k 行的 X 改成 Y"，并列出改了哪几处、每处为什么。
5. **复杂度**：单独给出**学员代码的复杂度**并与正解对比——TLE 类问题的答案通常就在这里。

## 语气

- 不要说"这里写错了"就完事——学员需要的是**下次自己怎么发现**。
- 学员的思路如果是对的（只是实现挂了），明确说"思路没问题"，这对他很重要；如果思路本身错了，也要直说，并给一个能判定的理由（反例或复杂度）。
- 不要为了显得严谨而含糊："可能是边界问题"是废话，"`l=0` 时你的 `while` 第一次就访问 `a[-1]`"才是诊断。
