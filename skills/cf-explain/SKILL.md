# 讲解（Explain a problem）

**核心原则：先想清楚，再讲清楚；顺序是"推理链"，不是"章节清单"。**

## 0. 先判断要不要跑验证

| 情况 | 做法 |
|---|---|
| 会话里已经有这题**验证通过**的产物（`cf_workspace` 显示 `verification.status == "ok"`） | **不要重复对拍**。直接用已有产物讲解。 |
| 会话里没有产物，用户要完整讲解 | 走下面的对拍流程（见 `cf-verify`），**先验证后讲解**。 |
| 用户只是追问上一条讲解 | **不要跑任何链路**。这是普通对话：历史在上下文里，直接回答他问的那一点。 |

> 追问是最容易被做坏的地方。用户问"这两个公式怎么来的"，答案就是那两行公式的推导，**不是**再生成一份完整讲义。宁可短、准、直击，也不要重新铺一遍全题。

## 1. 讲解的结构（按这个顺序想，按这个顺序说）

1. **这题在问什么**——只写容易读错的地方，不复述题面。
2. **突破口**——一句话。如果你不能压缩成一句话，说明你还没想清楚。
3. **为什么这么想**——这是最值钱的一段。必须给依据：代价分析、交换论证、或者是"别的方法为什么不行"。不要写"因为这样最优"。
4. **走一遍**——一个具体的小数据，每一步的数都写出来。学员是跟着这个例子理解的，不是跟着公式。
5. **正确的算法**——可执行的步骤。
6. **复杂度**——怎么算出来的，以及为什么能过（对着数据范围说）。
7. **代码**——与已验证的代码**逐字一致**（这是硬要求，改一个字学员就拿不到分）。
8. **会踩的坑**——这题真正会踩的 1–3 个。

**关于第 2–4 段**：如果你觉得某段没内容可写，就跳过它，不要为了凑结构写空话。反过来，如果某个观察特别反直觉，就把它展开讲透——篇幅应该跟着"哪里难"走，而不是平均分配。

## 2. 语气与颗粒度

- **面向学员的真实水平**（信息卡里的 rating）：1400+ 不要讲语法和模板；1800+ 直接讲关键观察与正确性，代码按逻辑分块，不逐行念。
- 自检：某个 1200 分选手看了会觉得"这不是废话吗"的句子，删掉。
- **不许编造动机**：代码里哪些地方是踩坑才加的防御，只能来自真实的对拍轨迹。轨迹里没有的，就说"这里是为了稳妥"。
- 验证通过时**不要**复盘对拍过程，也不要写"我已反复验证"。一句话带过。
- 验证**没**通过时（`verification.status != "ok"`）：**开头第一句就如实说明**"这题我还没能验证通过"，然后只讲有把握的部分，代码必须标注"未经验证"。绝对禁止暗示已经验证。

## 3. 交付形式（完整讲解 = 图文文档，这是硬要求）

- **完整讲解的交付物是"对话正文 + 一份图文文档"**：最后一步**必须**调用 `cf_doc` 产出 HTML 文档。
  正文只留 1–2 句引子 + 关键结论（不要把文档内容再复述一遍，文档就渲染在消息下面）。
  这一点没有例外：学员点开就是"图文讲解"，只给 Markdown 会被当成没做完（真实反馈两次都是这个原因）。
- 只有这两种情况**不**出文档：① 用户明确只要思路（"给点思路 / 先别给答案"）；② 你只是在追问里补一句解释。
- 文档至少要 1 张**真图解**（有节点与连线的 SVG；**表格不算图**，把表格画成 SVG 也不算）。
  画哪张：算法状态怎么一步步变、数据结构长什么样、构造怎么摆、或者反例/边界长什么样。
  但**不要凑图**：删掉它讲解并不变差，它就不该存在；第二张只在真的还有一处说不清时才画。
- 文档只是承载形式，**内容要求与上面完全一致**（推理链优先，不要按模板分节）。
