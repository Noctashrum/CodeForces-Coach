# 图文文档（Rich HTML document）

产出是一份**正文片段**，由应用的设计系统接管样式与交互，在沙箱 iframe 里渲染，用户可以边看边点。

**完整规范见本 skill 目录下的 `DESIGN.md`——动手前先读它**（class 白名单、SVG 规范、交互组件写法、硬性规则）。

## 用法

```
cf_doc { html: "<div class=\"wrap\">…</div>", title: "CF 1800C 贪心+堆", intro: "一两句引子" }
```

工具会：校验 → 净化（修可修的）→ 包裹设计系统与 CSP → 落盘到工作区 → 返回可打开的路径。
校验失败会把**具体错误**返回给你，改完重试一次；第二次仍失败就退回 Markdown（不要假装成功）。

## 内容要求（比格式重要）

1. **文档只是承载形式**。内容要求与 `cf-explain` 完全一致：推理链优先（突破口 → 为什么 → 走一遍 → 算法 → 复杂度 → 代码 → 坑），**不要按模板填空**。
2. **至少 1 张图（硬性：一张都没有会被判不合格）；通常 2 张**。但图是"讲清楚"的手段，不是装饰：
   画之前先问自己 **"把这张图删掉，学员会不会变难懂？"** 不会 → 别画（凑数的图比没有图更糟：占篇幅、还稀释重点）。
   - **值得画**：算法状态随步骤变化（扫描/双指针/单调栈/并查集/DP 转移）、数据结构或几何的形态、
     构造题的摆放方案、正确性论证（贪心交换为什么可行）、**反例/边界的最小构造**、暴力 vs 正解的量级对比；
   - **不值得画**：纯数学推导与复杂度计算、输入输出格式与模板、"开始→读入→循环→输出"的空壳流程图、
     把样例数组原样抄一遍、只在标题写"示意图"却没有具体数字的图；
   - **画在哪**：图放在**推理最难的那一步**旁边，不要平均分布在每一章；第二张只在真的还有一处说不清时才画
     （同一个点的另一个角度也算凑数）。
3. **篇幅按内容走**。写之前先想"哪一段最需要展开"，把篇幅给它。不要平均分配。
4. **代码必须与已验证的代码逐字一致**（校验器会比对；手改一个字就会被打回）。
5. 验证结论只写**一行**（"官方样例通过 · 随机对拍 40 组一致"）。验证没通过时，在文档**开头**如实说明。
6. 文档外面（消息正文里）只写 1–2 句引子，不要把内容重复一遍。

## 常见失败原因

| 报错 | 原因 | 怎么改 |
|---|---|---|
| `标签未闭合` / `输出被截断` | 写太长，被输出上限截断 | 砍掉次要章节，确保正常收尾 |
| `缺少结构：需要一个 div.wrap` | 忘了最外层 `wrap` | 用骨架包起来 |
| `用了设计系统之外的 class` | 自造 class | 只用 `DESIGN.md` 里的 class |
| `文档里出现了 LaTeX` | 写了 `$x$` / `\le` | 用 `.formula` / `.fx` 排版 |
| `没有任何 SVG 图解` | 通篇纯文字 | 挑"最难用文字说清的那一步"画一张（不是随便找章塞装饰图） |
| `文字 x=… 超出 viewBox` | SVG `<text>` 越界 | 调 x/y 或放大 viewBox |
